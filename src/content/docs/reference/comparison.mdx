envGo is intentionally narrow. This page makes the trade-offs explicit so you can decide in 2 minutes whether it fits your project.

## What envGo has

- **Zero-dependency single binary** — `CGO_ENABLED=0`, standard library only, `go vet`/`go test` clean. No Node, no Python, no runtime to install. ~8 MB (7.7–8.5 MB across the six released targets; not UPX-packed).
- **Static server + secure proxy** — serves your `index.html` and injects `{VAR}` server-side. The browser only sees placeholders and `window.EnvLoaded[NAME]=true`.
- **Scan-to-open on a phone** — `--qr` binds every interface and prints a scannable QR of the LAN URL; `--qr-format png` adds a PNG file for terminals that mangle block characters.
- **Two modes** — Local (`/proxy` + per-process token `X-EnvGo-Token`, checked with `Host` + `Origin` + `subtle.ConstantTimeCompare`) and Public (`/api/<name>` fixed routes from `envgo.routes.json`).
- **Outbound allowlist** — proxying is off until you pass `--allow host1,host2`, so a misconfigured route cannot become an open relay.
- **Per-route gateway** — `vars` allow-set, per-route `rate_limit` (fixed-window), optional bearer `auth`, request shaping via `query`/`headers`/`body`, and `scrub_response` through `logger.Redact`.
- **DNS-rebinding defence** — a closed allowlist of `Host` values built from the bound address, so a hostile domain resolving to `127.0.0.1` is still refused with 403.
- **Hot-reload** — `internal/envstore` polls `.env` every 1.5 s with no restart; `/__envgo/reload` pushes an SSE event so an open page refreshes itself.
- **Dashboard (metadata only)** — `GET /__envgo_dashboard` shows variable *names* and the last 200 requests, never values.
- **Diagnostics** — `GET /__env.js` typo detection (Levenshtein ≤3) with red banner, PHP `echo getenv` warning, missing `vars` warning at startup.
- **PHP** — executes `.php` via the `php` binary (CLI or `-cgi`) with `.env` injected, 30 s timeout, header parsing.
- **TLS** — `--tls` self-signed, and the certificate carries the LAN address so a phone scanning over HTTPS gets a matching name.
- **Scaffolding and deploy files** — `envgo init` writes a project template; `envgo deploy` generates `Caddyfile`, `nginx.conf` and a `Dockerfile` from your config.
- **Self-update** — `envgo run update` fetches the latest release, best-effort-checks it against the published `SHA256SUMS`, then startup-tests the binary with `-h` before replacing itself.
- **Cross-platform** — `make release` builds darwin/linux/windows `amd64`+`arm64` as six plain binaries.
- **AI-friendly** — one copy-paste prompt (`/envgo-agent-prompt.txt`) that teaches any agent to `envgo -v` → auto-install → `envgo init` → `envgo run dev`.

## What envGo does not have

Be explicit about this before you commit:

- **No database, no sessions, no user auth.** The token is per-process, not per-user. Any page on your own origin can fetch it.
- **No auto-HTTPS.** `--tls` is self-signed for dev. Production TLS is your reverse proxy (Caddy does Let's Encrypt).
- **No unlimited abuse protection by default.** `default_rate_limit` is empty → *unlimited* until you set `30/min` etc. Rate limiting is also per-process and needs `trust_proxy: true` behind a proxy.
- **No streaming scrub.** SSE passthrough skips redaction to avoid buffering — an upstream that echoes a secret in a stream leaks it.
- **No build step.** envGo serves files as-is. It does not bundle, minify, or transpile JS.
- **No secret rotation / vault.** It reads a flat `.env` file. For Vault/AWS Secrets Manager, sync to `.env` yourself.
- **No multi-tenant isolation.** One `.env`, one gateway config per process. For per-user keys, you need a real backend.
- **No shared concurrency story.** Rate limits and request history are per-process, so scaling out means scaling those out too.
- **No atomic self-update.** `envgo run update` checks the new binary, but if the final swap fails it leaves it beside the old one and asks you to replace it by hand.

If you need any of the above, envGo is the wrong tool — use Next.js/Nuxt API routes or a Worker.

## When to choose what

| You are... | Pick |
|---|---|
| Beginner, designer, AI agent that just generated `index.html` and needs to call OpenAI without learning Node | **envGo** |
| Want to open the thing on your phone right now, with no tunnel account | **envGo** |
| Already building a SPA with Vite and comfortable writing a small proxy handler | Vite proxy |
| Building a full app with DB, auth, SSR | Next.js / Nuxt |
| Already running Caddy/nginx in prod and want `templates` or `header_up` | Caddy/nginx |
| Need global edge, KV, or pay-per-request | Workers / Functions |

## Bottom line

envGo is not a replacement for a backend. It is a **bridge for the gap between “I have a static HTML file” and “I need one secret without learning a framework.”** If that gap is your project, envGo is the shortest path. If you have already crossed that gap, stick with what you have.
